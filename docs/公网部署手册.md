# 公网部署手册

> 目标:把 Stage 0 验证过的本机服务,安全地暴露到公网,让任意浏览器访问。
> 预计耗时:1–2 小时(主要花在证书和路由器上)
>
> 前置:**Stage 0 必须已通过**(见 [Stage0-验证手册](Stage0-验证手册.md))。
> 本文只讲"怎么做",原理和取舍见 [架构设计 §7.5 / §7.6](架构设计.md)。

---

## 部署总览

五件事,按顺序做:

```
① 确认公网 IP ──▶ ② 配 DDNS ──▶ ③ 签 TLS 证书 ──▶ ④ 改 MediaMTX 配置 ──▶ ⑤ 路由器端口映射
                                                                              │
                                                                              ▼
                                                                     从 4G 网络验证
```

**顺序不能乱。** 证书里要写域名(②的先决条件),配置里要填证书路径(③的先决条件)。

完成清单:

- [ ] 确认是真公网 IP(不是 CGNAT)
- [ ] 域名解析指向本机公网 IP,且能自动更新
- [ ] 拿到该域名的有效 TLS 证书
- [ ] MediaMTX 开启 TLS + 鉴权,推流端口绑定回环
- [ ] 路由器映射 `8443/TCP` 和 `8189/UDP`
- [ ] Windows 防火墙放行上述端口
- [ ] 用**手机 4G**(非 WiFi)验证能看

---

## 一、确认公网 IP

### 1.1 判断是否有真公网 IP

1. 登录路由器后台,找到 **WAN IP / 外网 IP**(不要看 LAN IP / 内网 IP)
2. 浏览器打开 https://www.whatismyip.com 或百度搜「IP」
3. **两者一致** = 有真公网 IP;**不一致** = 在 CGNAT 后面

CGNAT 下端口映射**完全无效**,本手册的其余部分都不必做了 —— 需要改用 VPS 中转或 Tailscale。

### 1.2 常见的假公网 IP 段

如果路由器 WAN IP 落在下面这些段,一定是 CGNAT:

```
100.64.0.0/10     运营商级 NAT 专用段(最常见)
10.x.x.x          私有地址
172.16–31.x.x     私有地址
192.168.x.x       私有地址
```

## 二、配置 DDNS

家宽的公网 IP 会变(重拨号、运营商回收),需要一个域名始终指向当前 IP。

### 2.1 准备域名

- 任意注册商购买即可
- **用海外注册商**(Cloudflare / Namecheap 等),家宽自建无需备案
- 把该域名的 **DNS 托管**到支持 API 解析的服务商(推荐 Cloudflare,免费且 API 完善)

### 2.2 三种 DDNS 实现方式

| 方式 | 适用 | 说明 |
|---|---|---|
| **路由器自带 DDNS** | 首选 | 路由器后台找 DDNS / 动态域名,多数支持花生壳、No-IP、DynDNS |
| **服务商 API + 脚本** | 灵活 | 用 Cloudflare API 定时更新 A 记录,可跑在任务计划里 |
| **DDNS 客户端软件** | 兜底 | 在本机装客户端,但多一个常驻进程 |

**推荐顺序:先看路由器有没有。** 有的话配置量最小,而且不依赖本机开机。

### 2.3 验证

```cmd
nslookup share.example.com
```

比对返回的 IP 和路由器 WAN IP。一致即成功。

> IP 变化后 DDNS 需要几分钟生效。如果发现服务突然不可用,先查 IP 是否变了。

## 三、签发 TLS 证书

### 3.1 为什么必须用 DNS-01 验证

**国内家宽的 80/443 端口经常被运营商封禁。** Let's Encrypt 的 HTTP-01 验证需要 80 端口可达,会直接失败。

**DNS-01 验证不依赖任何入站端口** —— 它通过在域名 DNS 里添加一条 TXT 记录来证明所有权。这是家宽自建场景唯一可靠的方式。

### 3.2 用 acme.sh 签证书

acme.sh 是纯 shell 脚本,在 **Git Bash** 里就能跑(不需要 WSL)。

```bash
# 安装
curl https://get.acme.sh | sh

# 配置 DNS 服务商凭据(以 Cloudflare 为例)
export CF_Token="你的Cloudflare_API_Token"

# 签发
~/.acme.sh/acme.sh --issue --dns dns_cf -d share.example.com

# 安装到指定位置
mkdir -p tools/mediamtx/certs
~/.acme.sh/acme.sh --install-cert -d share.example.com \
  --key-file       tools/mediamtx/certs/server.key \
  --fullchain-file tools/mediamtx/certs/server.crt
```

> 其他 DNS 服务商把 `dns_cf` 换成对应的 `dns_xxx`,`CF_Token` 换成相应环境变量。
> Cloudflare API Token 在后台「My Profile → API Tokens」创建,权限只需 `Zone:DNS:Edit`。

**备选方案:** [win-acme](https://www.win-acme.com/) 是 Windows 原生工具,有图形界面,但也需要配置 DNS 验证插件。

### 3.3 验证证书

```bash
openssl x509 -in tools/mediamtx/certs/server.crt -noout -subject -dates
```

确认 `CN` 是你的域名,且有效期正确。

### 3.4 自动续期

Let's Encrypt 证书 **90 天过期**。必须配置自动续期,否则三个月后服务突然中断。

```bash
# acme.sh 默认会装一个 cron;Windows 上需要确认它在跑
~/.acme.sh/acme.sh --cron
```

Windows 上更可靠的做法是**建一个任务计划**,每 60 天执行一次续期并重新安装证书,然后重启 MediaMTX。

> ⚠️ 证书更新后**必须重启 MediaMTX** 才会加载新证书。

## 四、修改 MediaMTX 配置

用架构设计附录 B.1 的配置替换 `tools/mediamtx/mediamtx.yml` 中的相应部分:

```yaml
# ── WebRTC / WHEP 服务(对公网) ──
webrtc: yes
webrtcAddress: :8443
webrtcEncryption: yes
webrtcServerKey: certs/server.key
webrtcServerCert: certs/server.crt
webrtcLocalUDPAddress: :8189
webrtcAllowOrigin: '*'

# ── ICE 候选(公网成败关键) ──
webrtcIPsFromInterfaces: no
webrtcAdditionalHosts: [share.example.com]

# ── 推流入口(仅本机,不映射到公网) ──
rtmp: yes
rtmpAddress: 127.0.0.1:1935
srt: yes
srtAddress: 127.0.0.1:8890

# ── 路径与鉴权 ──
paths:
  live:
    readUser: viewer
    readPass: <换成一个强密码>
    publishUser: publisher
    publishPass: <换成一个强密码>
```

### 四个容易配错的点

| # | 配置项 | 错了会怎样 |
|---|---|---|
| 1 | `webrtcAdditionalHosts` 填的是**域名**不是 IP | 填 IP 在 IP 变动后会失效;填内网 IP 则公网永远连不上 |
| 2 | `webrtcIPsFromInterfaces: no` **必须关** | 不关的话浏览器会优先拿到内网地址,浪费一轮 ICE 探测,可能直接失败 |
| 3 | `rtmpAddress` 绑 `127.0.0.1` 而非 `:1935` | 绑 `0.0.0.0` 等于给公网开了推流权限(叠加上路由器没映射才勉强安全,但不应依赖) |
| 4 | 密码不要用默认值或弱口令 | 公网端口会被扫描,弱口令等于没有 |

### 启动验证

```cmd
cd tools\mediamtx
mediamtx.exe
```

**预期日志**:

```
INF [WebRTC] listener opened on :8443 (HTTP/HTTPS)
INF configuration loaded
```

如果报证书加载失败,检查路径是否相对于 `mediamtx.yml` 所在目录。

## 五、路由器端口映射

### 5.1 找到设置位置

各品牌叫法不同,常见于:

- 端口转发 / Port Forwarding
- 虚拟服务器 / Virtual Server
- NAT 转发 / 端口映射
- 应用管理 / 应用列表

通常在「高级设置」或「安全」分类下。

### 5.2 添加两条规则

| 名称 | 外部端口 | 内部 IP | 内部端口 | 协议 |
|---|---|---|---|---|
| ShareScreen-WHEP | 8443 | 192.168.x.x | 8443 | TCP |
| ShareScreen-ICE | 8189 | 192.168.x.x | 8189 | **UDP** |

**内部 IP** 填运行 MediaMTX 那台机器的内网地址。

> 建议在路由器里**给这台机器绑定静态 DHCP**(MAC 绑定固定 IP),否则机器重启后 IP 变化,端口映射就指向别处了。

### 5.3 不要映射的端口

| 端口 | 协议 | 原因 |
|---|---|---|
| 1935 | TCP | RTMP 推流入口 —— 映射出去等于让任何人都能覆盖你的画面 |
| 8890 | UDP | SRT 推流入口 —— 同上 |

**只映射 8443/TCP 和 8189/UDP。** 这是最重要的安全边界。

### 5.4 同步放行 Windows 防火墙

**管理员权限**命令行:

```cmd
netsh advfirewall firewall add rule name="ShareScreen WHEP" dir=in action=allow protocol=TCP localport=8443
netsh advfirewall firewall add rule name="ShareScreen ICE" dir=in action=allow protocol=UDP localport=8189
```

> 路由器映射和 Windows 防火墙是**两层独立的拦截**。两个都要放行,少一个都不通。

## 六、验证

### 6.1 从外部网络验证(关键)

⚠️ **必须用手机的蜂窝数据,关掉 WiFi。** 用家里的 WiFi 测试等于在局域网内访问,测不出公网链路的任何问题。

手机浏览器打开:

```
https://share.example.com:8443/live?user=viewer&pass=<播放密码>
```

**预期**:出现证书锁标志(无安全警告)+ 实时画面。

### 6.2 逐层排查

如果失败,从外到内逐层验证:

| 层级 | 验证命令 | 预期 |
|---|---|---|
| DNS | 手机浏览器打开 `https://share.example.com:8443` | 能连上(报错也行,关键是**不是超时**) |
| 端口映射 | 从外部 `telnet share.example.com 8443` | 能连上 |
| TLS | 浏览器地址栏有锁标志 | 证书有效、域名匹配 |
| 鉴权 | 不带凭据访问 | 返回 401 |
| 播放 | 带凭据访问 | 出画面 |

### 6.3 记录实际延迟

用秒表法(同 Stage 0):手机拍一张同时包含真实秒表和浏览器画面的照片,时间差即端到端延迟。

**公网预期:200–500ms。** 明显更高说明链路有问题。

## 七、安全加固检查

公网暴露后,逐项确认:

- [ ] 推流端口(1935 / 8890)未映射到公网
- [ ] 推流端口在 MediaMTX 配置里绑定 `127.0.0.1`
- [ ] 播放路径设置了 `readUser` / `readPass`
- [ ] 密码是强口令,不是 `123456` 之类
- [ ] 播放端口用的是 8443 而非默认的 8889
- [ ] 启用了 TLS(否则鉴权凭据明文过公网)
- [ ] 观看链接(含凭据)没有发到公开场合

### 关于观看链接里的凭据

MediaMTX 的鉴权凭据通过 URL 查询参数传递,**会出现在浏览器历史记录和服务器日志里**。个人自用可接受,但注意:

- 不要把带凭据的链接截图发到公开群组
- 界面上的二维码包含凭据,同样注意传播范围

## 八、日常维护

| 周期 | 事项 |
|---|---|
| 每次使用前 | 确认 DDNS 域名解析正确、MediaMTX 已启动 |
| 每 60 天 | 确认证书自动续期任务执行成功 |
| 不定期 | IP 变动后检查 DDNS 是否跟上 |

### 快速自检命令

```bash
# 域名解析是否正确
nslookup share.example.com

# 证书还有多久过期
openssl x509 -in tools/mediamtx/certs/server.crt -noout -enddate

# 端口是否在监听
netstat -ano | findstr "8443 8189"
```

### 服务中断时的排查顺序

```
1. 域名解析还对不对?(IP 变了 / DDNS 挂了)
2. 证书过期了吗?
3. MediaMTX 进程还在吗?
4. ffmpeg 还在推流吗?
5. 宽带重拨号导致 IP 变了?
```

大多数"突然不能用了"都是**公网 IP 变动而 DDNS 没跟上**。

## 九、当前已知限制

这些是端口映射直连拓扑的固有限制,不是配置问题:

| 限制 | 说明 |
|---|---|
| **上行带宽** | 观众数上限 = `上行 × 0.7 ÷ 码率`。家宽上行普遍偏低,多人同时观看往往不可行 |
| **跨运营商质量** | 家用电信 + 观众用移动,晚高峰可能明显卡顿 |
| **对称 NAT 观众** | 部分移动 4G/5G 网络下可能打不通,当前拓扑没有 TURN 兜底 |
| **公网 IP 变动** | 依赖 DDNS 跟上,有延迟窗口 |

完整分析见 [架构设计 §7.6.7](架构设计.md)。
