# 屏幕共享软件 —— 架构设计

> 状态:主体已完成 —— 屏幕/窗口采集、硬件编码、音频、MediaMTX 分发、控制页、
> 托盘、目录式发布、公网部署、**远程控制(鼠标/键盘/剪贴板)** 均已实现并实测通过。
> 未做的部分见 §11。
> 最后更新:2026-10-07

---

## 1. 项目目标

Windows 平台屏幕共享工具。服务端采集本机画面,客户端通过**浏览器**访问观看,无需安装任何客户端软件。

**核心需求**

| 项 | 内容 |
|---|---|
| 服务端平台 | Windows 10 1809+ |
| 客户端 | 任意现代浏览器(Chrome / Edge / Firefox / Safari) |
| 网络环境 | **公网访问** —— 家宽公网 IP + 端口映射直连(无 VPS) |
| 交互模式 | 观看 + **远程控制**(默认关闭,需主机逐次批准,见 §12) |
| 同时观众数 | **常规 1 人**,上限 3 人(需降档)。由上行带宽推导,见 §7.6.5 |
| 画质 | **60fps 为硬性要求**;分辨率/码率可在界面自选,见 §6.5 |
| 采集源 | ① 屏幕/窗口(内建) ② OBS 虚拟摄像头 |
| 界面风格 | 扁平化 |
| 使用场景 | 个人自用,非商业分发 |

**非目标(当前阶段明确不做)**

- 文件传输、多屏切换(远程控制本身已实现,见 §12)
- VPS 中转 / CDN 分发(当前采用端口映射直连,见 §7.6)
- 音频传输
- 多用户账号体系
- 移动端原生 App

## 2. 设计原则

按重要性排序,冲突时以序号小的为准:

1. **能跑起来 > 架构优雅。** 个人自用工具,先验证链路,再谈优化。
2. **难的部分外包给成熟组件。** 采集交给 ffmpeg,WebRTC 服务端交给 MediaMTX。自己只写胶水。
3. **每一层可独立替换。** 现在选快的方案,但接口要清晰,以便后续换掉任何一层而不影响其他层。
4. **不引入构建负担。** 拒绝需要自编译数小时的依赖(如 libwebrtc)。

## 3. 总体架构

```
                         采集源
    ┌──────────────────────────────────────────────┐
    │                                              │
    │  ① 屏幕 / 窗口          ② OBS                │
    │     (gdigrab)             ├─ WHIP 直推 ★推荐  │
    │                           └─ 虚拟摄像头(dshow)│
    └───────┬───────────────────────────┬──────────┘
            │                           │
            ▼                           │
    ┌───────────────┐                   │
    │    ffmpeg     │                   │
    │  采集 + 硬编   │                   │
    └───────┬───────┘                   │
            │  H.264 + Opus             │  H.264(零转码)
            │  RTSP                     │
            ▼                           ▼
    ┌───────────────────────────────────────────────┐
    │              MediaMTX                         │
    │   (单二进制流媒体服务器,含 WebRTC 栈)          │
    │   输入:RTMP / SRT / WHIP / RTSP               │
    │   输出:WHEP / HLS                             │
    └───────────────────┬───────────────────────────┘
                        │ WHEP (WebRTC over SRTP + TLS)
                        ▼
            ┌───────────────────────────┐
            │   路由器端口映射            │
            │   TCP 8443  /  UDP 8189   │
            └─────────────┬─────────────┘
                          │ 公网
        ┌─────────────────┴──────────────────┐
        │  https://share.<域名>:8443/live     │
        │  浏览器直接打开,内置播放器           │
        │  (局域网内观众可走内网 IP,见 §7.3) │
        └────────────────────────────────────┘
```

**自定义网络代码量为零。** 全部由 MediaMTX 承担:信令、ICE、DTLS、SRTP、RTP 打包、SDP 协商。

公网访问带来的额外约束(ICE 候选、TLS、鉴权、上行带宽)集中记录在 §7.6。

## 4. 技术选型

### 4.1 选型结果

| 层 | 选型 | 理由 |
|---|---|---|
| 采集 | `ffmpeg` 子进程 | 屏幕/窗口/摄像头三种源统一在一条命令行里 |
| 编码 | `ffmpeg` + `h264_nvenc`(或 qsv/amf,兜底 libx264) | 硬件加速,零自研代码 |
| 传输 | **MediaMTX** | 单二进制,自带 WebRTC 服务端和网页播放器 |
| 控制界面 | Go 单二进制 + 内嵌 localhost 网页 | 同时满足"单文件分发"和"扁平化 UI" |
| 打包 | Go `go build` 交叉产出 exe | 无运行时依赖 |

### 4.2 备选方案与否决理由

这些方案都评估过,**当前阶段**不采用,但保留为后续演进路径。

#### 否决:纯 Rust(webrtc-rs + windows-rs + Media Foundation)

技术上最优——采集/编码/传输可在同一进程内完成,理论上能做到 D3D11 纹理零拷贝进编码器,画质和 CPU 占用最好。

**否决原因:启动成本过高。** Media Foundation 在 Rust 里没有高层封装,`IMFTransform` / `MFTEnumEx` 那套 COM 调用需要手写大量 unsafe,预计占整个项目一半开发时间。与"快速能用"的目标直接冲突。

**保留为长期演进方向**(见 §11)。

#### 否决:纯 C++(libdatachannel)

采集和编码环节最贴 Windows 原生。libdatachannel 作为 WebRTC 库比 libwebrtc 轻量得多,CMake 即可构建,且支持投递预编码的 H.264 样本。

**否决原因:COM 生命周期管理和手写 SDP 的繁琐度,对个人自用工具是过度投入。** 且相比 ffmpeg 方案没有决定性优势。

#### 否决:C# / .NET

WGC 调用和窗口选择 UI 的开发效率最高。

**否决原因:核心链路有硬伤。** WebRTC 生态薄弱——`SIPSorcery` 的 H.264 支持和性能都偏弱;`Microsoft.MixedReality.WebRTC` 官方已弃用。长处(UI)恰好不是本项目的难点,短板恰好是要害。

#### 否决:WebCodecs + WebTransport

延迟和带宽都很优秀。

**否决原因:要求 secure context(HTTPS)。** 局域网部署要用户信任自签证书,体验灾难。这条限制直接判死刑。

#### 未采用:HLS / LL-HLS

浏览器兼容性最好,HLS.js 一行搞定。

**未采用原因:延迟 2–5 秒。** 屏幕共享场景体感太差,不满足实时性。

#### 未采用:WebSocket + MJPEG

实现极简,延迟尚可。

**未采用原因:带宽 30–100 Mbps。** 虽然局域网带宽充裕,但编码效率太低,没有理由选它。

### 4.3 关于 OBS 集成的方案取舍

OBS 有两条接入路径,**两条都保留,默认走 WHIP**。

| 方案 | 链路 | 延迟 | 评价 |
|---|---|---|---|
| **WHIP 直推** ★ | OBS →(WebRTC)→ MediaMTX | ~100ms | OBS 29+ 原生支持。H.264 零转码零重编。**推荐** |
| 虚拟摄像头 | OBS → DirectShow → ffmpeg → MediaMTX | +150ms | OBS 版本低时兜底;好处是 ffmpeg 统一管理所有源 |

虚拟摄像头路径的固有代价:输出为未压缩 NV12/YUY2(1080p60 ≈ 3 Gbps 内存拷贝),且要经过"编码→解码→重新编码"两次有损链路。

## 5. 采集层

三种源,统一由 ffmpeg 处理。

### 5.1 屏幕 / 显示器

**两种实现,程序默认用 gdigrab,可选 ddagrab(DXGI Desktop Duplication)。**

> 性能上 ddagrab 实测比 gdigrab 快一个数量级(见 §5.4),但**默认值是 gdigrab**:
> ddagrab 依赖驱动和显卡,个别机器上抓不到画面,而默认值必须保证"点开始就有
> 画面"。要性能的用户自己到界面上选「屏幕(GPU 采集)」。

```
-f lavfi -i "ddagrab=framerate=60"
```

- GPU 侧采集,输出 d3d11 硬件帧,可直接零拷贝进 NVENC
- 只能抓整块桌面,**不支持单窗口**
- 独占全屏应用切换时可能返回 `ACCESS_LOST`,ffmpeg 内部会自动重建
- `draw_mouse` 默认为 1(光标画进画面)。远程控制开启时程序会显式传
  `draw_mouse=0`,理由见 [§12.11](#1211-光标控制者看自己的)

**缩放只能走 CPU(实测结论):**

ddagrab 输出的 d3d11 帧**无法**用 `scale_d3d11`(报 `Unsupported pixel format`)或 `hwmap=derive_device=cuda`(报 `Function not implemented`)处理,GPU 侧缩放两条路都不通。只能回落到 CPU:

```
-vf "hwdownload,format=bgra,scale=1280:800"
```

`hwdownload` 会产生一次 CPU 拷贝 —— 2560×1600 BGRA = 16.4 MB/帧,60fps 下约 983 MB/s。**这是整条采集链路的实际瓶颈**,但实测仍能稳定跑满 60fps(见 §5.4)。

**gdigrab(程序的默认源):**

```
-f gdigrab -framerate 60 -i desktop
```

- 兼容性最好,零配置
- ⚠️ 抓的是原始 BMP,CPU 拷贝极重,实测帧率只有 ddagrab 的一半
- ⚠️ 抓到的是屏幕对应区域,**窗口被遮挡时会抓到遮挡物**(见 §5.2)

### 5.2 单个窗口

```
-f gdigrab -framerate 60 -i title="窗口标题" -vf "scale=1280:800"
```

⚠️ **窗口采集只能走 gdigrab** —— ddagrab 基于 DXGI Desktop Duplication,只能抓整块桌面,不支持单窗口。这是本项目**唯一必须使用 gdigrab** 的场景。

- `title=` 匹配**标题包含该字符串**的窗口
- ⚠️ **已知缺陷:窗口被遮挡时会抓到遮挡内容**。gdigrab 本质是抓屏幕对应区域,不具备 WGC 的合成感知能力
- ⚠️ gdigrab 性能本就比 ddagrab 差一个数量级(§5.4),叠加窗口采集后**能否稳定跑满 60fps 存疑**,需实测(见 §10 的 R3)
- 若上述缺陷不可接受,需升级到 WGC 采集(见 §11)

### 5.3 OBS 虚拟摄像头

```
-f dshow -i video="OBS Virtual Camera"
```

- 设备名以实际枚举结果为准,可用 `ffmpeg -list_devices true -f dshow -i dummy` 查看
- 分辨率/帧率由 OBS 画布决定,ffmpeg 参数无法覆盖
- ⚠️ 输出为未压缩帧,ffmpeg 需要完整解码再编码,CPU 开销明显高于另外两种源

### 5.4 采集性能实测(2026-10-03)

**测试环境:** RTX 5060 Laptop GPU + Intel UHD,桌面 2560×1600 @ 240Hz,ffmpeg 9.0.2,gdigrab/ddagrab 均为整屏采集。

#### 采集方式对比(请求 30fps,输出 1280×720)

| 方式 | 实际帧率 | 丢帧 | 结论 |
|---|---|---|---|
| gdigrab | 25fps | **19** | ✗ 跟不上 |
| **ddagrab** | 29–30fps | **1** | ✓ |

gdigrab 抓的是原始 BMP 流(`bitrate: 3932172 kb/s`,约 3.9 Gbps),CPU 拷贝是瓶颈。**性能上 ddagrab 完胜。**

不过程序默认仍用 gdigrab:ddagrab 在部分显卡/驱动/远程桌面会话下直接抓不到画面,
而默认值要的是"一定能用"。性能取舍见 §5.1。

#### 帧率上限探测

| 请求帧率 | 实际交付 | 说明 |
|---|---|---|
| 60fps | 57–58fps | 不加 cfr 时的默认行为 |
| 120fps | ~66fps | DDA 轮询的时钟上限 |
| 60fps + `-fps_mode cfr` | **60.0fps** | ✓ 精确,`drop=0` |

⚠️ **必须加 `-fps_mode cfr`**,否则输出会稳定漂移到 57–58fps。加了之后精确恒定,靠复制帧补齐。

DDA 的原始新帧交付上限约 **66fps**,所以 60fps 目标下只有约 10% 余量 —— 屏幕剧烈变化时可能偶尔掉帧。

#### 瓶颈定位

| 环节 | 实测能力 | 是否瓶颈 |
|---|---|---|
| NVENC 编码(2560×1600@60) | **308fps(5.13x)** | ✗ 有 5 倍余量 |
| ddagrab 采集 | ~66fps | ✓ **实际瓶颈** |

裁剪采集区域到 1280×800 **不改变**交付帧率(仍是 58fps),说明瓶颈是 DDA 的轮询时钟,不是内存带宽。

#### 已排除的方案

| 方案 | 结果 |
|---|---|
| `scale_d3d11` | ✗ `Unsupported pixel format` |
| `hwmap=derive_device=cuda` + `scale_cuda` | ✗ `Function not implemented (-40)` |
| `scale_npp` | ✗ 此构建未包含 |

**结论:GPU 侧缩放不可用,只能 `hwdownload` 回 CPU 缩放。**

#### 双显卡说明

本机是 Intel UHD + RTX 5060 的混合架构,但显示器由 **RTX 5060 直接驱动**(240Hz),所以不存在跨 GPU 拷贝问题。若换到显示器接在核显上的机器,ddagrab 采集的帧需要跨 PCIe 送到 NVENC,性能可能显著下降 —— 那种情况下应改用 `h264_qsv`(在核显上编码)。

**这一点现在由程序自己处理了**(2026-10-06):启动时枚举显示适配器,找出驱动主显示
器的那块,把同厂商的编码器排到最前 —— 显示器在核显上就优先 `h264_qsv`。判据与
边界见 §6.1。

> ⚠️ **注意这条改动本身还没有在"显示器接核显"的机器上实测过。** 本机显示器挂在
> NVIDIA 上,正好走的是"厂商匹配"那一支,不匹配的那条路只有单元测试覆盖。
> 如果换机器后发现选出来的编码器反而不如以前,把配置里的编码器手动指定成
> `nvenc` 即可绕过 —— 手动选择排在候选列表最前。

### 5.5 音频(实测结论)

**ffmpeg 采集不到系统声音。** 这不是配置问题,是 Windows 上的结构性限制:

| 途径 | 结果 |
|---|---|
| ffmpeg 的 WASAPI 输入设备 | ✗ 本构建不提供(`-devices` 里只有 dshow / lavfi / openal 等) |
| DirectShow 的「立体声混音」 | ✗ 本机声卡有这个端点,但被 Windows 禁用了(程序无法自行启用);现代声卡普遍干脆不再提供 |
| ffmpeg 的 openal 输入 | ✗ 无论填什么设备名都返回 `Invalid Value` |
| DirectShow 第三方滤镜(`virtual-audio-capturer`) | 需额外安装驱动并注册,给分发引入一个重量级依赖 |
| **自己做 WASAPI 回环采集** | ✓ 见 `internal/audio`;也是目前采用的方式 |
| 由 OBS 采集后推流 | ✓ 备选,见 §5.6 |

所以桌面音频由程序自己采:`IMMDeviceEnumerator` 取默认播放设备 →
`IAudioClient` 以 `AUDCLNT_STREAMFLAGS_LOOPBACK` 打开 → `IAudioCaptureClient`
拉 PCM。全程按 vtable 下标调 COM,不引入 CGO。

采到的是**渲染设备正在输出的声音**,也就是"你听到什么,观众就听到什么";
换耳机、切 HDMI、插蓝牙都会自动跟随,不需要用户改任何系统设置。

> ⚠️ **"默认设备"不一定是有声音的那一台。** 实测踩到:笔记本接 HDMI 显示器之后,
> 系统默认播放设备指到了显示器那一路输出,而声音其实还从笔记本自己的扬声器出来
> —— 回环采默认设备只采到静音,观众那边就是"有画面、一点声音没有"。程序无从
> 知道声音到底从哪台设备出来,所以**必须让用户能指定**:`AudioConfig.DeviceID`
> 为空表示跟随默认设备,否则走 `IMMDeviceEnumerator::GetDevice` 打开指定端点
> (见 `internal/audio` 的 `ListDevices` / `OpenDevice`)。
>
> 指定的设备不在时(拔了耳机)**退回默认设备并给出提示**,而不是让整个共享没有
> 声音 —— 出声比"设备对得上"重要,但这件事得说出来,否则用户以为自己选的那台
> 正在被采。
>
> 注意每台设备的混音格式是**各自独立**的:实测蓝牙耳机是 44100Hz,板载扬声器是
> 48000Hz。所以格式必须跟着实际打开的那台设备走,不能按默认设备缓存一份。

两个实现上的坑值得记下来:

1. **结构体不能用 Go 直接映射。** Win32 的 `WAVEFORMATEX` 是紧凑的 18 字节,
   而 Go 会把结构体尺寸补齐到 4 的倍数(20)。嵌进 `WAVEFORMATEXTENSIBLE`
   之后子格式 GUID 落在偏移 28 而不是 24 —— 差这 4 个字节的后果是格式识别
   永远失败。改成按显式字节偏移读。
2. **静音时收不到任何数据包。** 回环模式下桌面没有声音时引擎根本不产生数据,
   `GetNextPacketSize` 一直返回 0。而 ffmpeg 是按连续流处理的 —— 一个字节都
   收不到它就一直在那儿等,**连输出都打不开**(症状是画面也一起出不来)。
   所以静音必须按墙上时钟自己补,模拟真实采集设备的连续输出。

#### 音频只能是 Opus,所以推流只能是 RTSP

浏览器的 WebRTC 只支持 Opus 和 G.711,而 MediaMTX **不做转码**。

实测(2026-10-03):推一路 H.264 + AAC 的 RTMP 流进 MediaMTX,再用三种 SDP
offer 分别做 WHEP 握手:

| offer 声明的编码 | 结果 |
|---|---|
| 只有 H264 | ✅ 返回正常应答 |
| H264 + Opus | ❌ `codecs not supported by client` |
| H264 + MPEG4-GENERIC(AAC) | ❌ `codecs not supported by client` |

RTMP 能带的音频只有 AAC,所以要送声音就必须换容器。**本程序一律走 RTSP +
Opus** —— 实测 MediaMTX 收到 RTSP 里的 H.264 + Opus 后,路径状态是
`ready: true`、轨道 `[H264, Opus]`,WHEP 应答里两路都是 `a=sendonly`,
浏览器两端都能收到。

OBS 是另一条路:它走 WHIP,音频本来就是 Opus,MediaMTX 原样透传。但 OBS 如果
改用 RTMP 推,同样只有画面 —— 控制页上两个地址都给出,并标注了这一点。

## 6. 编码层

### 6.1 编码器选择

| 优先级 | 编码器 | 适用 |
|---|---|---|
| 1 | `h264_nvenc` | NVIDIA 显卡 |
| 2 | `h264_qsv` | Intel 核显 |
| 3 | `h264_amf` | AMD 显卡 |
| 4 | `libx264` | 软件兜底,CPU 开销大 |

这张表的顺序只是**默认**。实际选择由三层决定,缺一不可:

**第一层:厂商亲和(`internal/gpu` + `ffmpeg.Plan`)。**

`EnumDisplayDevices` 枚举显示适配器,找出**驱动主显示器**的那块,把同厂商的
硬件编码器排到最前。理由见 §5.4:ddagrab 抓的是驱动显示器那块 GPU 的画面,
编码若落在另一块卡上,帧要跨 PCIe 走一趟。

判据是 `StateFlags & PRIMARY_DEVICE`,**不是枚举顺序** —— 混合显卡笔记本上
第 0 项未必是主输出。认不出来(无头机、纯 RDP 会话、只有虚拟显示器)就退回
默认顺序,不影响启动。

顺带要跳过的:虚拟显示器驱动(向日葵的 `OrayIddDriver`、Parsec VDD、RDP 的
remote display adapter)。它们没有 `PCI\VEN_xxxx` 前缀,统一归为"未知"。
另外每块适配器会**按输出重复出现**(本机实测一块卡出现 4 次),要按 DeviceID 去重。

**第二层:启动时真跑一遍(`ffmpeg.ProbeUsable`)。**

`ffmpeg -encoders` 给的是**构建期列表**,和机器上插着什么卡无关:装的是完整
构建时,一台只有 A 卡的机器照样会列出 `h264_nvenc`。实测(Intel UHD + RTX 5060,
无 A 卡):

```
列表里有: h264_nvenc、h264_qsv、h264_amf、libx264
真跑:     h264_amf → [AMF] DLL amfrt64.dll failed to open
```

所以拿到候选之后要用合成画面各编一帧,把跑不起来的剔掉。四个并发跑约 1.2 秒
(瓶颈是 `h264_qsv` 的初始化)。

两处刻意的保守:超时视为"不确定"→ 保留(别误杀忙碌机器上的编码器);
全部失败 → 返回原列表(说明探测本身出了问题,不该把选择权清零)。

用的是 `testsrc` 合成源而**不是 ddagrab** —— DXGI Desktop Duplication 同一
时刻只允许一个采集会话(见 §12.5 那条约束的同一来源),拿它探测会和真正的
采集打架。

**第三层:发起推流时逐个回退(`stream.Manager.runStart`)。**

按候选列表逐个试,起不来就换下一个。这一层**不能省**:合成源是软件帧,只能
证明"编码器能初始化",证明不了 ddagrab 的 d3d11 硬件帧零拷贝路径可用。

两类失败要分开,否则一个和编码器无关的错误会被候选数乘一遍:

| 失败 | 处理 |
|---|---|
| ffmpeg 报 `Error while opening encoder` / 缺 DLL 之类 | 换下一个候选 |
| 其余(窗口标题写错、采集源不可用) | 原地重试,换谁都没用 |

用户手动指定的编码器排在最前,起不来则顺延 —— 会回退,但**不会静默回退**,
控制页上会写明「首选 xxx 在本机起不来,已自动改用 yyy」。回退是运行时状态,
**不写回配置**:配置里存的是用户的偏好,写进去等于悄悄改掉它。

### 6.2 低延迟参数(关键)

以下参数**不可省略**,否则延迟会显著劣化:

| 参数 | 作用 |
|---|---|
| `-fps_mode cfr` | **强制恒定帧率**。不加会从 60 漂移到 57–58fps(见 §5.4) |
| `-g 60` | 每 60 帧一个关键帧(60fps 下即 1 秒)。WebRTC 依赖关键帧做流切换和快速起播 |
| `-bf 0` | **禁用 B 帧**。B 帧需要重排序缓冲,是低延迟的头号杀手 |
| `-tune ll` / `-zerolatency` | 关闭前瞻,编码器不缓冲多帧 |
| `-rc cbr` | 恒定码率,避免网络突发 |
| `-pix_fmt yuv420p` | 保证浏览器兼容性 |

### 6.3 参考参数

**完整命令(实测可用,60fps @ 1280×800):**

```bash
ffmpeg -f lavfi -i "ddagrab=framerate=60" \
  -vf "hwdownload,format=bgra,scale=1280:800" \
  -fps_mode cfr \
  -c:v h264_nvenc -preset p4 -tune ll -rc cbr \
  -b:v 3M -maxrate 3M -bufsize 3M \
  -g 60 -bf 0 -pix_fmt yuv420p \
  -f flv rtmp://127.0.0.1:1935/live
```

> 这是 2026-10-03 在本机实测跑通的命令,`speed≈0.99x`、`drop=0`。
>
> 输出段后来从 `-f flv rtmp://…:1935` 改成了 **RTSP**(原因见 §5.5 — RTMP 带不了
> Opus 音频)。画面相关的参数一个都没动,音频加上之后仍然 `fps≈60`、`drop=0`。
>
> ⚠️ 上面这条是 **ddagrab** 的输入段,也就是界面上的「屏幕(GPU 采集)」。
> **程序默认用的是下面 gdigrab 那段**(§5.1 的取舍)。

**gdigrab 输入段(程序的默认源,把上面那段输入换成它):**

```bash
ffmpeg -f gdigrab -framerate 60 -i desktop \
  -vf "scale=1280:800" \
  -fps_mode cfr \
  -c:v h264_nvenc -preset p4 -tune ll -rc cbr \
  -b:v 3M -maxrate 3M -bufsize 3M \
  -g 60 -bf 0 -pix_fmt yuv420p \
  -f flv rtmp://127.0.0.1:1935/live
```

**libx264 兜底(无硬件编码器时):** 把 `-c:v h264_nvenc -preset p4 -tune ll` 换成 `-c:v libx264 -preset ultrafast -tune zerolatency`。

#### 默认档位:原始分辨率 @ 60fps @ 3 Mbps

**默认不缩放。** 实测结论:零拷贝路径既避开了缩放带来的模糊,又省掉一次 CPU 拷贝(§5.4);而且 H.264 对静止区域几乎不耗码率,提高分辨率并不显著增加带宽占用。需要压码率时再手动选小一档。

分辨率预设跟随桌面宽高比生成,不写死 16:9(§6.5)。

**为什么是 3 Mbps:** 上行是硬瓶颈,而**上行 = 观众数 × 码率**(§7.6.5)。3 Mbps 是个保守默认值,上行偏低时也够支撑单人观看。

**⚠️ 60fps 的画质代价(必须知道):**

码率固定时,帧率翻倍意味着**每帧可分到的比特数减半**:

| 档位 | 每像素比特数 |
|---|---|
| 1280×800 @ 30fps @ 3M | 0.098 bpp |
| 1280×800 @ 60fps @ 3M | **0.049 bpp** |

屏幕内容(文档、代码、静态 UI)压缩率极高,受影响不大。但**动态画面**(视频播放、快速滚动、游戏)在 60fps + 3Mbps 下会明显发糊 —— 这时候降低分辨率比保持分辨率更划算。

**如果画质不满意,优先调分辨率而不是帧率:** 1024×640@60 @ 3M 是 0.073 bpp,比 1280×800@60 好 50%。

### 6.4 编码档位

| 参数 | H.264 Profile | 说明 |
|---|---|---|
| 默认 | 不指定,交给编码器 | 通常输出 High profile |
| 兼容优先 | `-profile:v main` | 兼容性更好 |
| 出问题时 | `-profile:v baseline` | 最保守,用作排障手段 |

⚠️ WebRTC 的 SDP 需要正确的 `profile-level-id`。MediaMTX 会解析 SPS 自动生成 fmtp,正常情况无需干预;若浏览器报编解码器协商失败,优先尝试降 profile。

### 6.5 可调参数

分辨率、帧率、码率、编码器**全部暴露给用户自选**,不做写死。

| 参数 | 可选值 | 默认 |
|---|---|---|
| 分辨率 | 原始 / 1920×1080 / 1600×1000 / 1280×800 / 1280×720 / 1024×640 | **1280×800** |
| 帧率 | **60** / 30 / 20 / 15 | **60** |
| 码率 | 1 / 2 / 3 / 4 / 6 / 8 / 12 Mbps,及自定义输入 | 3 Mbps |
| 编码器 | 自动 / nvenc / qsv / amf / x264 | 自动 |

> **分辨率预设应跟随桌面宽高比。** 16:10 的桌面套用 16:9 的档位会同时产生拉伸和上下黑边。
> 程序在启动时读取桌面分辨率来生成预设列表,而不是写死。

#### 运行时修改的方式:重启 ffmpeg 进程

⚠️ **ffmpeg 无法在运行中修改采集帧率、分辨率和码率。** 这三者都绑定在进程启动参数上,没有可用的热更新接口。

修改参数的做法是:**终止当前 ffmpeg 进程 → 用新参数重新启动**。观众侧表现为约 1–2 秒黑屏中断,随后恢复。

这个代价可以接受 —— 参数调整是低频操作,且个人自用场景对短暂中断不敏感。**不要为了消除这 1 秒去引入 zmq 过滤器之类的方案**,`zmq` 在 ffmpeg 中是实验性特性、默认不编译进 Windows 构建,且多数编码器对运行时改码率的支持并不完整。

**例外:** 走 OBS 路径时,码率可以在 OBS 界面动态调整(编码在 OBS 侧),不受此限制。

#### UI 必须给出的实时反馈

参数面板不能只是几个下拉框。因为**上行带宽是硬约束**,用户选了 1080p@12M 却只能支撑 1 个观众,这件事必须当场告诉他,而不是等他开了分享发现卡顿才反应过来。

| 提示项 | 计算方式 |
|---|---|
| 预估上行占用 | = 码率 |
| 可支撑观众数 | = 实测上行 × 0.7 ÷ 码率 |
| 超限警告 | 观众数逼近可支撑数时标红提示 |

#### 预设档位(按上行带宽推荐)

用户首次运行时填入实测上行带宽,程序据此推荐档位。**推荐逻辑:在满足目标观众数的前提下取最高画质。**

全部按 **60fps** 计算:

| 实测上行 | 可用(70%) | 支撑 1 人 | 支撑 2 人 | 支撑 3 人 |
|---|---|---|---|---|
| 10 Mbps | 7 Mbps | 1920×1080@6M | 1280×800@3M | 1280×720@2M |
| 20 Mbps | 14 Mbps | 1920×1080@12M | 1920×1080@6M | 1280×800@4M |
| 40 Mbps | 28 Mbps | 1920×1080@12M | 1920×1080@12M | 1920×1080@8M |

这张表是**推荐值**,不是限制,用户仍可任选。它存在的意义是让用户在动手调之前就有一个合理起点。

#### 配置持久化

参数存本地配置文件(JSON),下次启动沿用。切换采集源时参数保留,但分辨率默认值例外 —— OBS 虚拟摄像头受 OBS 画布限制,应显示为"跟随 OBS"。

## 7. 传输层(MediaMTX)

### 7.1 职责边界

MediaMTX 承担**全部** WebRTC 相关工作,是本方案代码量能压到接近零的关键:

- SDP 协商(offer/answer)
- ICE 候选收集与连通性检查
- DTLS 握手与 SRTP 加解密
- RTP 打包 / 解包
- H.264 的 SPS/PPS 处理与 fmtp 生成
- 内置网页播放器(浏览器访问即用,无需自写前端)

### 7.2 端口分配

> **注意:** 下表是 Stage 0 调试用的默认值。**公网部署时播放端口改为 8443 并启用 TLS**,推流端口绑定回环。见 §7.6.2 和附录 B.1。

| 端口 | 协议 | 用途 |
|---|---|---|
| **8889/tcp** | HTTP | **WHEP 拉流 + 内置播放器页面(WHEP 默认端口)**(公网部署改为 8443 + TLS) |
| 8189/udp | UDP | WebRTC ICE(媒体流实际走这里) |
| 8888/tcp | HTTP | HLS 输出,当前不用(⚠️ 别和 WebRTC 的 8889 搞混) |
| 1935/tcp | RTMP | ffmpeg 推流入口(**禁止映射到公网**) |
| 8890/udp | SRT | ffmpeg 推流入口(低延迟备选,**禁止映射到公网**) |
| 9997/tcp | HTTP | API(默认关闭,用于查询观众数)**禁止映射到公网** |
| 8554/tcp | RTSP | 备用入口,当前不用 |

> ⚠️ **已实测确认:** MediaMTX v1.21.1 的 WebRTC 默认端口是 **8889**,HLS 才是 8888。
> 所以默认配置下播放地址是 `http://localhost:8889/live`,不是 8888。

⚠️ **防火墙需放行 8889/tcp 和 8189/udp**,否则其他设备无法观看。

### 7.3 局域网内访问

> 本节仅覆盖局域网内观看。**公网访问的 ICE 配置是另一回事,见 §7.6.4** —— 两者不能混用。

浏览器从**同网段的其他设备**访问时,ICE 候选必须包含服务端的局域网 IP。MediaMTX 默认 `webrtcIPsFromInterfaces: yes`,会自动从网卡收集 IP,通常无需配置。

若观看失败,在配置中显式指定:

```yaml
webrtcAdditionalHosts: [192.168.1.100]   # 替换为实际局域网 IP
```

⚠️ 公网部署时**必须**改成域名并把 `webrtcIPsFromInterfaces` 关掉 —— 否则浏览器会拿到内网地址,公网观众永远连不上(§7.6.4)。

### 7.4 推流入口对比

| 入口 | 延迟 | ffmpeg 支持 | OBS 支持 | 用途 |
|---|---|---|---|---|
| RTSP | 低 | ✅ 原生 | ✅ 原生 | **本程序推流走这个** —— 只有它携带 Opus(§5.5) |
| RTMP | 中 | ✅ 原生 | ✅ 原生 | 仅为兼容 OBS 保留;只能带 AAC,所以没有声音 |
| WHIP | 最低 | ✅ 9.0 起有 `whip` muxer | ✅ 29+ | OBS 直推走这个 |

> 本文档早期版本在这里写过"ffmpeg 不支持 WHIP 输出(没有对应 muxer)"。那是
> ffmpeg 8 之前的情况 —— 9.0.2 的 `-muxers` 里确实有 `whip`。
>
> 但本程序最终没有用它:实测 ffmpeg 的 WHIP muxer 向 MediaMTX 发出 offer 后
> 读不到应答(`Failed to read response`),MediaMTX 那边的会话建了就立刻
> `closed: terminated`。怀疑是 offer 里的 `a=setup:passive`(客户端要求当 DTLS
> 服务端,而 WHIP 的设计是服务端当)MediaMTX 不认,但没有继续深挖 ——
> RTSP 一次就通了,没必要。


### 7.5 安全说明

⚠️ **公网暴露后,鉴权从"可选"变成"必须"。**

MediaMTX 默认配置**无任何鉴权**。公网 IP 的开放端口会在数小时内出现在扫描日志里,这不是理论风险。后果很具体:

- **播放路径无鉴权** = 任何知道地址的人能看到你的屏幕
- **推流路径无鉴权** = 任何人都能推流覆盖你的画面

**加固清单(公网部署必须全部完成):**

| # | 措施 | 说明 |
|---|---|---|
| 1 | 路径级鉴权 | `paths.live.readUser` / `readPass` 保护播放;`publishUser` / `publishPass` 保护推流 |
| 2 | 不暴露推流端口 | 8554 / 1935 **不映射到公网**,推流只走本机回环 |
| 3 | 监听到回环 | 推流端口绑定 `127.0.0.1` 而非 `0.0.0.0` |
| 4 | 非常规端口 | 播放端口不用 8888,改 8443 之类,减少被扫概率 |
| 5 | 强制 TLS | 否则鉴权凭据以明文经公网传输(见 §7.6) |
| 6 | 凭据不写死在页面 | 观看链接带凭据时,不要在公开页面硬编码 |

第 2、3 条是最容易忽略也最致命的 —— 只映射播放端口,推流端口留在内网,能挡掉绝大多数攻击面。

### 7.6 公网访问设计

**拓扑决策:端口映射直连,不使用 VPS。**

选用理由:本机有真公网 IP,省掉一台服务器。代价是**上行带宽成为不可绕过的硬瓶颈**(见下方带宽规划),且观众数上限被家宽上行锁死。

#### 7.6.1 前提条件

开工前必须确认两项,任一不满足则本方案不成立:

| # | 条件 | 确认方式 |
|---|---|---|
| 1 | 家宽有**真公网 IP** | 路由器 WAN IP == `whatismyip` 查到的公网 IP |
| 2 | 上行带宽足够 | 实测上传速率(见 §7.6.5),不要信套餐宣传值 |

#### 7.6.2 端口映射清单

| 公网端口 | 协议 | 内网目标 | 用途 | 备注 |
|---|---|---|---|---|
| **8443** | TCP | `192.168.x.x:8443` | WHEP 信令 + 播放器页面(TLS) | 必须 |
| **8189** | UDP | `192.168.x.x:8189` | WebRTC 媒体流 | 必须,最易漏 |
| 1935 | TCP | —— | RTMP 推流入口 | ❌ **不要映射** |
| 8890 | UDP | —— | SRT 推流入口 | ❌ **不要映射** |

⚠️ **两个最常见的失败原因:**

1. **只映射了 TCP,漏了 UDP 8189。** 表现是:页面能打开、播放器一直转圈。WebRTC 的媒体流走 UDP,和信令端口是两回事。
2. **把 1935 映射出去了。** 等于向公网开放推流权限,任何人都能覆盖你的画面。

#### 7.6.2.1 自动映射(UPnP)

上表那两条映射可以由程序自己建,不必用户进路由器后台 —— 见 `internal/portmap`。
默认关闭,控制页勾选后启用。

实现上值得记下来的几点:

- **外部端口等于内部端口**(8889、8189),不做端口翻译。UDP 本来就只能这样:
  `webrtcAdditionalHosts` 只接受主机名,端口由 MediaMTX 自己补成
  `webrtcLocalUDPAddress` 的值,所以外网端口不同就直接连不上。
  这也是它和手动方案(8443 → 8889)不能混用的原因。
- **四个 UPnP 服务变体都得试。** `WANIPConnection` v1/v2 和 `WANPPPConnection` v1
  分布在内网网关的两个版本包里,命中哪个取决于 WAN 口怎么拨号而不是版本新旧。
  实测华为路由 AX3 Pro(WS7200-10)**只提供 `WANPPPConnection:1`**。
- **SOAP 请求要显式设超时。** goupnp 的 `soap.NewSOAPClient` 不设,
  零值 `http.Client` 等于永不超时,一台半死的路由器能把调用方永久挂住。
- **要重试。** 同一台华为路由器偶发地在 SOAP 请求上直接断连(报 EOF),
  实测 7 次里出现 2 次,重发即成功。SOAP fault 是路由器的明确答复,不该重试 ——
  两者的区别就是 `isTransient`。
- **失败必须优雅降级。** 找不到网关、CGNAT、冲突、多重 NAT 都要退回手动路线,
  绝不能影响启动。判定 CGNAT 要单独看 `100.64.0.0/10` ——
  `net.IP.IsPrivate()` 不包含这一段。
- **退出时不删映射。** 崩溃路径删不掉,两种退出方式行为不一致反而更糟;
  残留映射指向一个已死的端口,本身无害,靠租约自然过期。只有用户主动取消勾选
  才撤掉。

#### 7.6.3 地址稳定性(DDNS)

家宽公网 IP 会变。需要:

- 一个域名(海外注册商,家宽自建无需备案)
- DDNS 客户端,定时把域名解析更新到当前公网 IP

然后 `webrtcAdditionalHosts` 填**域名**而不是 IP:

```yaml
webrtcAdditionalHosts: [share.example.com]
webrtcIPsFromInterfaces: no
```

#### 7.6.4 ICE 候选配置(公网成败的关键点)

**这是端口映射方案能不能成功的唯一关键点。**

WebRTC 不是"连上端口就完事"。MediaMTX 在 WHEP 应答里返回一组 ICE 候选地址,浏览器拿这些地址去连媒体流。默认收集的是网卡本地 IP:

```
candidate: ... 192.168.1.100 8189 typ host
```

公网浏览器拿到 `192.168.1.100` **永远连不上** —— 那是内网地址,在互联网上不可路由。症状是信令通了但媒体流永远建立不起来。

必须显式声明公网地址(见 §7.6.3 配置)。改完后检查 WHEP 应答,候选里应出现域名或公网 IP。

#### 7.6.5 上行带宽规划

**WebRTC 每个观众是一路独立的 SRTP 流,上行 = 观众数 × 码率。** 没有多播可用,浏览器不支持,所以这个乘法无法用协议优化绕开。

**上行必须实测,不能拿套餐标称值推算。** 家宽普遍是非对称的 —— 下载充裕、上传被运营商锁死在低位,两者常相差十倍以上。要测的是**上传**。

> 测法:关掉其他占网的程序,speedtest 选同城同运营商节点,记上传值。
> **至少测两次 —— 白天一次、晚高峰一次,按最差的那次规划。**
> 测速结果是突发速率,通常比持续推流偏乐观,建议再乘 0.6~0.7 后再用。

为协议开销和其他网络活动**保留 30% 余量**,剩余部分按观众数均分:

| 实测上行 | 可用(70%) | 1 人 | 2 人 | 3 人 |
|---|---|---|---|---|
| 5 Mbps | 3.5 Mbps | 720p@3M | 480p@1.5M | 480p@1M |
| 10 Mbps | 7 Mbps | 1080p@6M | 720p@3M | 720p@2M |
| 25 Mbps | 17 Mbps | 1080p@12M | 1080p@8M | 720p@6M |
| 50 Mbps | 35 Mbps | 1080p@12M | 1080p@12M | 1080p@12M |

**由此得出的设计约束:**

- **界面必须实时显示「当前设置能支撑几个观众」**,算法就是 `上行 × 0.7 ÷ 码率`(见 §6.5)。档位超出承载要当场标红,而不是等用户自己发现卡顿
- **默认按保守值取**(原始分辨率 @ 60fps @ 3 Mbps),上行偏低时也能用
- 观众数超出承载时**只能降档** —— 见 §7.6.8

⚠️ 上行是硬上限,不随观众数弹性伸缩。超出后不是排队,是所有人一起卡。

#### 7.6.6 带宽优化措施

| 措施 | 效果 | 实现 |
|---|---|---|
| **无观众时不推流** | 空闲时上行归零 | 监测 WHEP 连接数,为 0 时停止 ffmpeg |
| 默认档位 | 1280×800 @ 60fps @ 3 Mbps | 见 §6.3 |
| 按观众数分档 | 2 人时降到 1024×640 @ 1.5M | 需重启 ffmpeg(ffmpeg 运行中无法改码率) |
| 降分辨率(优先) | 1024×640@60 比 1280×800@60 少 36% 像素 | 60fps 下这是比降帧率更好的选择 |
| 降帧率(次选) | 30fps 省约 40% 码率 | 60fps 是需求,只在极端情况下用 |

⚠️ **ffmpeg 无法在运行时修改码率**,动态调整只能靠重启进程。若这个能力重要,OBS 路径可以动态调(编码在 OBS 侧)。

#### 7.6.7 已知限制

这些是**端口映射直连拓扑的固有限制**,不是实现缺陷:

1. **上行带宽是硬上限。** 观众数上限 = 上行 ÷ 码率,软件层面无法突破。
2. **跨运营商质量差。** 你家用电信、观众用移动,晚高峰可能明显卡顿。国内互联互通问题,无解。
3. **观众数超出上行承载时会全体劣化。** 不是排队,是大家一起卡。
4. **依赖公网 IP 不变。** CGNAT、IP 变动、运营商策略调整都可能中断服务。
5. **浏览器侧对称 NAT 可能失败。** 服务端有公网 IP 时通常能打通(浏览器主动发起,服务端从请求中学到对方地址);但若观众在严格对称 NAT 下(部分 4G/5G),需要 TURN 兜底 —— 而当前拓扑没有可用的 TURN 服务器。

#### 7.6.8 超出上行承载时怎么办

⚠️ **本方案明确不使用 VPS**(见 §1 非目标),因此超出上行承载时,可选手段只有降档:

| 手段 | 效果 | 代价 |
|---|---|---|
| 降低码率 | 观众数按比例增加 | 画质下降 |
| 降低分辨率 / 帧率 | 同上 | 清晰度 / 流畅度下降 |

**没有第三条路。** 上行是物理约束,协议层优化无法突破 —— 每个观众都是一路独立的 SRTP 流,不存在多播。

**判断依据:如果「观众数 × 目标码率 > 上行 × 0.7」,就只能降档。**

> 注:§11 记录了 VPS 中转方案。那是唯一能打破"上行 = 观众数 × 码率"这个乘法的手段,但当前已排除。除非未来需求显著增长,否则不要走这条路。

#### 7.6.9 两个地址:一个能选、一个不能选

控制页上有两个地址下拉,它们**不是同一类东西**,这是这一节唯一要说的事。

| | 用户能不能改 | 为什么 |
|---|---|---|
| **链接里显示的内网地址**(`LanHost`) | **能** | 多网卡时自动挑的那块未必是同伴能连上的(本机就有 astral 和 WLAN 两块) |
| **端口映射指向的内网地址** | **不能** | 那是路由表决定的事实,不是偏好 |

第二行是踩出来的:UPnP 的 `NewInternalClient` 曾经拿到过一个不属于路由器局域网
的地址(`10.126.126.1`,某块虚拟网卡),路由器直接回 **402 Invalid Args**。
所以 `syncPortMapRules` 固定用路由表推导出来的地址,`LanHost` 只喂给
`watchURLs` / `remoteLinks`。有一个测试专门钉这条。

**公网那一侧反过来:能探测的就不该让人手填。** 程序已经掌握:

- **路由器报告的外网地址**(UPnP)—— 这是**权威来源**,只有它知道端口映射
  有没有真的建起来。下拉里的「自动」就是它,选了会跟着 IP 变。
- **外部回显服务探测到的地址** —— 只在路由器拿不到时才问,而且**绝不自动填写**。

> ⚠️ 为什么要这么小心:运营商级 NAT 下,回显服务照样返回一个漂亮的公网地址,
> 但那是运营商那台 NAT 的出口,映射不进来。拿它自动填会**悄悄产出一条打不开
> 的链接** —— 比留空更糟,因为留空至少在界面上看得见。
>
> 这个判断没法从外面做,只有路由器知道。回显服务在界面上标着"仅供参考"。

回显服务是本程序**唯一**一个对外请求,显式设了超时(零值 `http.Client` 等于
永不超时,见 §7.6 里 goupnp 那条同类教训),而且 UPnP 一有结果就停发。
服务清单是**实测挑的**、不是照抄常见服务:实测 `api.ipify.org` 和 `4.ipw.cn`
在目标网络都连不上,而 `ifconfig.me` 返回 IPv6(会被 `ExternalIPUsable` 挡掉),
所以那个"按顺序试几个"的设计是必需的而不是保险。

## 8. 控制界面

### 8.1 形态选择

采用 **Go 单二进制 + 内嵌 localhost 网页**。

| 方案 | 扁平化能力 | 分发 | 构建成本 | 结论 |
|---|---|---|---|---|
| Rust + egui | 中(无阴影/动效) | 单 exe | 低 | 观感上限低 |
| Rust + iced | 良 | 单 exe | 低 | 观感上限低 |
| Rust + Slint | 优 | 单 exe | 中 | 备选 |
| **Tauri** | 完全 | exe + WebView2 依赖 | 中高 | 备选 |
| **Go + 网页** ★ | 完全 | **单 exe** | **低** | **采用** |

控制界面用网页实现,意味着 CSS 能表达的扁平化效果它都能表达,**UI 表现力没有上限**。

与 Tauri 相比的优势:不需要 WebView2 运行时,不需要维护 Rust + Web 两套构建链,浏览器本身就是渲染引擎。

与 Rust 原生 GUI 相比的优势:如前所述,egui / iced 做不到真正的精致扁平。

**代价:** 控制界面以浏览器标签页形式存在,缺少"应用感"(无独立窗口、无任务栏图标)。后续可用系统托盘补足常驻体验(Go 的 `tray-icon` 或 `systray` 库)。

### 8.2 界面元素

第一阶段(MVP):

- 采集源选择:屏幕 / 窗口 / OBS
- 窗口标题输入(初版手填,后续做枚举+缩略图)
- **参数面板:分辨率 / 帧率 / 码率 / 编码器**(见 §6.5)
- **上行带宽手动填写**(作为"可支撑观众数"的计算基准)
- **可支撑观众数实时提示** —— 随参数联动,超限标红
- 当前观众数显示(读 MediaMTX 的 API 接口)
- 开始 / 停止按钮
- **公网观看地址**展示(复制即用;不带凭据,但链接本身是凭据,注意传播范围)

第二阶段:

- 窗口枚举 + 缩略图选择
- 上行带宽自动实测(替代手动填写)
- 编码器自动探测与回退
- 系统托盘常驻

### 8.3 进程模型

```
┌──── sharescreen.exe (Go, GUI 子系统,无控制台) ────┐
│                                                  │
│  托盘图标  ←─ 双击打开控制页 / 右键菜单            │
│  HTTP Server :8080  ←─ 控制界面(localhost)       │
│                                                  │
│  ├─ 子进程: mediamtx.exe                          │
│  └─ 子进程: ffmpeg.exe                            │
│                                                  │
│  启动时:定位两个工具 → 启动 mediamtx              │
│         → 按用户选择拼接 ffmpeg 命令并启动         │
│         → 打开浏览器、显示托盘图标                  │
│                                                  │
│  控制页挂一条 SSE 长连接(/api/alive),页面关掉    │
│  连接就断 → 程序整体退出(见 server/alive.go)      │
│                                                  │
│  改参数时:终止 ffmpeg → 用新参数重新启动           │
│           (约 1–2 秒中断,见 §6.5)                 │
└──────────────────────────────────────────────────┘
```

### 8.4 工具的来源:和 exe 放在一起

`internal/paths` 对外只有 `ResolveFFmpeg` / `ResolveMediaMTX` 两个函数,
按可执行文件所在目录、当前工作目录、系统 `PATH` 的顺序去找 `tools/` 下的
两个组件(见 `sidecar.go`)。

发布件因此是一个文件夹:

```
ShareScreen-1.3.1/
  ShareScreen.exe
  使用说明.txt
  tools/ffmpeg/bin/ffmpeg.exe
  tools/mediamtx/mediamtx.exe
```

**曾经有过一条"内嵌"路线:** 用 `go build -tags embed_tools` 把两个组件
`go:embed` 进二进制,编出一个 165 MB 的单文件,拷到哪台机器都能跑。已废弃,
理由是它把组件藏进了 exe 里 —— 用户看不见里面装着什么,版本对不上时既换不掉
也说不清,出问题时连"到底跑的是哪份 ffmpeg"都无从确认。8 MB 变 165 MB、
每次编译多花十几秒是次要的。

当时那段实现里有个值得记下的坑:`go:embed` 的路径**相对于声明它的包目录,
且不允许用 `..` 往外跳**,所以嵌入声明只能待在仓库根(`package main` 所在处),
`internal/paths` 里写 `//go:embed tools/...` 会去找 `internal/paths/tools/...`
然后报 "no matching files found"。

## 11. 后续演进路径

当前架构刻意做了分层,每层可独立替换,现在选"快"的方案**不会给未来挖坑**。

### 替换采集层(提升画质/降低 CPU)

用 **Windows Graphics Capture** 替换 ffmpeg gdigrab。

- 解决窗口遮挡问题(WGC 具备合成感知)
- GPU 侧零拷贝,CPU 占用大幅下降
- 支持动态窗口尺寸变化

实现语言首选 Rust(`windows` crate)或 C++。产出为独立采集模块,输出 H.264 到 MediaMTX,**传输层和 UI 完全不受影响**。

### 替换传输层(减少依赖)

用 **Pion**(Go)自写 WHEP 服务替换 MediaMTX。

- 去掉一个外部依赖
- 可自定义鉴权、观众管理、按需推流
- **浏览器端代码无需改动**(WHEP 是标准协议)

### 扩展功能

| 功能 | 实现路径 |
|---|---|
| 音频 | ✅ **已实现**,见 §5.5 —— WASAPI 回环 → 本地 TCP → ffmpeg 编 Opus |
| 录制 | MediaMTX 原生支持(配置 `record: yes`) |
| **突破上行瓶颈** | 见下方"改用 VPS 中转" |
| 观众鉴权 | MediaMTX 路径级鉴权已够用;要按人发凭据需自写 WHEP 服务 |
| 远程控制 | ✅ **已实现**,见 §12 —— 不必换传输层,单独开一条 WebSocket 就够了 |

### 改用 VPS 中转(突破上行瓶颈)

> ⚠️ **当前已排除,不作为计划内路线。** 保留此节仅作技术备查 —— 万一日后需求增长到"多人 + 高画质",这是唯一出路。在 1 人观看的需求下不需要。

把 MediaMTX 从家中移到 VPS,**架构其余部分完全不变**:

```
家中:ffmpeg ──SRT 推流──▶ VPS: MediaMTX ──WHEP──▶ 浏览器
                (只占一路上行,与观众数解耦)
```

改动范围:

- ffmpeg 的推流目标从 `127.0.0.1` 改成 VPS 地址(一个参数)
- MediaMTX 配置文件挪到 VPS(内容大部分复用)
- 家中不再需要端口映射
- 家中上行从 `观众数 × 码率` 降为固定的**一路**码率

这是本方案分层设计的价值所在 —— 传输层的位置变了,采集层和控制界面一行都不用改。

## 12. 远程控制

让观众**经主机批准后**操作被共享的这台电脑。实现于 `internal/remotectl`、
`internal/input`、`internal/clipboard`。

### 12.1 传输层不换,单独开一条通道

`§11` 里原本写着"远程控制需要引入 DataChannel,届时需重新评估传输层选型"。
实测下来不需要:

- **WHEP 是只读的**,没有反向通路,这一点没变;
- 但回传通路**不必**和视频走同一条连接。单独开一条 WebSocket 就够,
  视频链路(ffmpeg → MediaMTX → WHEP)一行都不用动。

```
观众浏览器 ──WHEP 拉流──► MediaMTX(原有链路)
            ──WebSocket──► internal/remotectl ──► internal/input(SendInput)
```

代价是多一个对外端口。默认**关闭**,不开启时不监听、不映射。

### 12.2 为什么用 WebSocket 而不是 SSE + POST

项目原本只有 SSE(见 `internal/server/alive.go`),而且理由是"节省依赖"。这里
没有沿用,原因不是延迟:

**HTTP 并发的到达顺序不保证。** 控制消息里"按下 / 抬起"是成对的,乱序的后果
是鼠标卡在按下状态。用 POST 上行就必须串行 `await` 每一条,而那等于给每个
事件加一个 RTT。"移动 → 点击"的先后则是另一个必答题,见 §12.5。

所以引入了 `github.com/coder/websocket`(纯 Go、零传递依赖)。

### 12.3 坐标映射:分母是 size-1

归一化坐标 → 屏幕像素 → `SendInput` 绝对坐标空间(0~65535)。

**分母必须是 size-1。** 绝对坐标的目标区间是闭区间 [0,65535],对应像素区间
[0,size-1];用 size 当分母会让画面最右一列和最下一行永远点不到。实测(主屏
2048×1280)六个探测点,四角误差 0 像素,中间点最大 1 像素:

| 请求归一化 | 实际落点 | 误差 |
|---|---|---|
| (0, 0) | (0, 0) | 0 |
| (1, 1) | (2047, 1279) | 0 |
| (0.5, 0.5) | (1024, 640) | 1 |
| (1, 0) | (2047, 0) | 0 |

**绝对坐标一律带 `MOUSEEVENTF_VIRTUALDESK`**(按整个虚拟桌面铺开),不是按
主显示器。理由:折算路径是"先按采集矩形算出屏幕像素、再按虚拟桌面折算",
这对"采集主屏"和"采集整个虚拟桌面"两种范围都成立;而"直接按主显示器折算"
只在采集范围恰好等于主屏时才对。单显示器时两个式子算出来的数完全一样,
所以这么做没有额外代价。

**采集矩形随采集源变**(`ffmpeg.CaptureRect`),这是最容易搞错的一处:

| 采集源 | 实际范围 |
|---|---|
| `ddagrab`(不带 `output_idx`) | **主显示器**一块 |
| `gdigrab -i desktop` | **整个虚拟桌面**(原点可能是负数) |
| `window` / `obs` | 位置不确定 → **禁用远控** |

### 12.4 输入注入

`internal/input`,只用 `golang.org/x/sys/windows`,不引入 CGO。

实测确认:**`x/sys/windows` 里有完整的 `VK_*` 常量(161 个),但没有
`SendInput` / `INPUT` / `MOUSEINPUT` / `KEYBDINPUT`** —— 这几个要自己定义,
用 `NewLazySystemDLL` 调,和 `internal/window` 一个写法。

三个坑:

1. **`INPUT` 在 amd64 下必须是 40 字节**(`uint32` + 4 字节填充 + 32 字节联合体)。
   联合体的对齐要求来自 `MOUSEINPUT` 里的指针成员,少了那 4 字节填充,
   `dwExtraInfo` 会整体错位。同一类问题在 `WAVEFORMATEX` 上踩过一次
   (见 §5.5),所以这里用编译期断言把三个尺寸钉死,对不上直接编不过。
2. **字母和数字没有 `VK_A`..`VK_Z` / `VK_0`..`VK_9` 命名常量**,按 ASCII 直算。
3. **UIPI 的失败是静默的。** 前台窗口以管理员身份运行时,注入会被系统丢弃,
   而 `SendInput` 的返回值和 `GetLastError` **都不会**报错(这是 MSDN 明写的)。
   所以只能提前查前台窗口的完整性级别(`ElevatedForeground`),而这个判断
   必须排除"我们自己也提权了"的情况 —— 那种时候注入过得去,报警就是误报。

键盘分两条路:带 Ctrl/Alt/Win 的走虚拟键码(保证快捷键),能产生文本的字符走
`KEYEVENTF_UNICODE`(观众用中文输入法打出来的词在主机上没有对应按键序列,
而且虚拟键码会被主机的键盘布局重新解释一遍)。非 BMP 字符要按 UTF-16 代理对
拆成两条事件。

### 12.5 注入队列:顺序是硬要求

移动和离散事件(按下/抬起、滚轮、按键)**走同一条队列**。分开的话,"先把鼠标
移到按钮上、再点击"会变成"先点击、再移过去",点中的是上一个位置的东西。

合并只发生在**队尾那个还没被取走的移动**上:观众的鼠标已经移到别处,中间那些
位置没有意义。被覆盖的是末尾元素,剩余事件的相对顺序不变。

队列满时丢的是移动,不是按下/抬起 —— 丢掉一个"抬起"会让主机的鼠标键永远
卡在按下状态。

### 12.6 控制权:单人 + 逐次批准

状态机在 `internal/remotectl/control.go`:同一时刻只有一个会话能操作,其余的人
照常看画面,他们的事件在进入注入队列**之前**就被丢掉。

两个取舍值得记下来:

- **不排队。** 已经有人在等批准时,后来者直接收到"忙"。排队看着更公平,但主机
  批准时批的是队列里的某一个人,观众会看到自己"申请成功"却还是动不了。
- **申请 60 秒过期。** 主机不在电脑前时,申请挂着既占名额又让观众永远等一个
  不会来的答复。

### 12.7 鉴权:两层

现在整个项目**没有其他鉴权**(播放路径是"链接即凭据",见 §7.5)。控制通道
加了两层:

1. **链接令牌**(`crypto/rand` 32 字节)。放在 URL 的 `#` 片段里 —— 片段不会
   发到服务器,所以页面本身的请求在访问日志里不带凭据。
2. **主机当场批准**。令牌只决定能不能连上来看;要操作必须主机点头。

即便链接泄露,陌生人也只能看、不能动 —— 这是它和观看链路的关键区别。

### 12.8 剪贴板

`internal/clipboard`,只做文本(`CF_UNICODETEXT`)。图片和文件体积经常到几 MB,
经 WebSocket 送会把控制通道堵住 —— 输入事件和剪贴板共用那条连接,堵住它的
后果是鼠标也跟着卡。

- **不需要 `LockOSThread`**:剪贴板不是 COM。`internal/audio` 里那个
  `LockOSThread` 是 COM 的要求,别照搬。但必须串行化,两个 `OpenClipboard`
  同时进行会互相失败。
- **用序列号判断变化**:`GetClipboardSequenceNumber` 内容一变就加一,比每
  800 毫秒读一遍内容便宜得多(剪贴板里可能躺着几 MB 的东西)。
- **防回环**:记住自己刚写进去的那段文本的哈希,轮询到它就不再推回去。
  实测:控制者写回主机之后,主机不会把同一段文本推回来。
- **拿到控制权时补送一次当前内容**。轮询只在变化时通知,而"先复制好东西、
  再连过去"是最常见的用法 —— 那段内容的变化发生在拿到控制权之前,不补这一下
  就永远送不出去。(实测发现的漏,已修。)
- `SetClipboardData` 成功后内存所有权归系统,**绝不能 `GlobalFree`**。

**这里绕开了 `(*uint16)(unsafe.Pointer(ptr))`。** 那种写法本身是对的(这块内存
来自 `GlobalAlloc`,不归 Go 的 GC 管),但 `go vet` 的 `unsafeptr` 检查会报
"possible misuse of unsafe.Pointer"。换成把 Windows 那边的地址自始至终当作
`uintptr` 参数传给 `RtlMoveMemory`,参与转换的只有 Go 这一侧的指针
(`unsafe.Pointer → uintptr`,这个方向是允许的,syscall 就是这么用的)。
功能一样,`go vet ./...` 保持干净。

### 12.9 关掉控制页的行为变了

远控开着的时候,**关控制页不再退出程序**(改为记日志,退出走托盘菜单)。

远控的典型用法恰恰是人不在电脑前,浏览器标签崩溃或被误关会把整个程序连带
杀掉 —— 而那个时候你没法重启它。远控没开时行为完全不变。

### 12.10 一个 Windows 错误码的坑

识别"端口被占用"时**不能用 `syscall.EADDRINUSE`**。实测:

```
第二次监听错误: bind: Only one usage of each socket address ...
  errno 数值 = 10048              ← 系统实际返回的
  syscall.EADDRINUSE 数值 = 536870914   ← Go 自己编的合成值
  errors.Is(err, syscall.EADDRINUSE) = false
```

两者对不上,照着写就永远识别不出来。见 `remotectl.wsaEADDRINUSE`。

### 12.11 光标:控制者看自己的

实测反馈是"远控延迟特别高,鼠标有拖拽感"。查下来**不是延迟问题,也不用换传输层**,
而是光标。

原因两件事叠在一起:

1. `#screen.controlling { cursor: none }` —— 拿到控制权时本地光标被隐藏;
2. 主机光标被 ffmpeg 画进了视频里(`ddagrab` / `gdigrab` 的 `draw_mouse` 默认都是 1)。

于是控制时画面上**唯一可见的指针,是 0.3–1 秒前的主机光标**。手动了指针没动、
然后追着跑 —— 这就是"拖拽感"的字面来源。

> **为什么观看能忍、控制不能。** 同样 0.3–1 秒,纯观看时没有任何本体感觉参照,
> 完全够用;一旦是自己操作,手眼回路的容忍度是 100ms 级,延迟立刻变得刺眼。
> 输入的 WebSocket 那条路本身是干净的(§12.5 的紧循环注入,局域网不到 20ms),
> 换掉 MediaMTX 自写 Pion WHEP 也不会有任何改善 —— 还是同一套 WebRTC、
> 同样的接收端抖动缓冲。所以这里改的是**指针的来源**,不是链路。

**做法:远控开启时,采集不再画主机光标;指针由控制端自己提供**(浏览器原生光标)。

原生光标零延迟、天然平滑,而且位置是准的 —— rc.js 的归一化映射(§12.3)与主机的
`MoveNorm` 用的是同一个采集矩形,实测误差 0–1 像素。所以**不需要**额外的光标位置
回传通道:`clipboardLoop` 那种 60Hz 推送只会换来一个 RTT 的延迟和更差的平滑度,
只在"主机自己动了鼠标"这一种情形下才多出价值,不值得。

不画光标**不影响帧率**:`ddagrab` 的 `dup_frames` 默认为 true(画面未更新时重复
上一帧),外面还有 `-fps_mode cfr`。实测 5 秒 300 帧、60fps、`drop=0`,NVENC
零拷贝路径不受影响。附带好处是纯指针移动时画面不变,那些重复帧几乎不占码率。

**门控依据是远控开关本身,不是"此刻有没有人持有控制权"。** 后者要求在有人取到
控制权的那一刻重启采集,会在会话中途黑屏 —— 比这更糟。

代价有两条,都是接受的:

- **`draw_mouse` 是采集阶段的选项,无法按观众区分。** 远控开着时,纯观看链接
  (MediaMTX 自带播放页)的人也看不到主机光标。
- **切换这个开关会重启采集**(黑屏约 2–5 秒,音频一起重启),因为它是 ffmpeg 的
  启动参数。见 `server.applyRemoteControl`。这个门控是 `ffmpeg.CaptureOptsFor`
  的**唯一**一处定义,多个调用点各写一遍迟早会分叉,而症状是"光标有时候画、
  有时候不画"。

被否决的选项:

| 选项 | 否决原因 |
|---|---|
| 保留两个光标(本地 + 画面里那个) | 画面里那个仍然拖在后面,拖拽感的视觉来源没消失,只是多了一个 |
| 跑两路采集,分别带和不带光标 | 两倍编码和上行带宽,为一个人的光标不值得 |
| 按"是否有人持有控制权"动态切换 | 会话中途重启采集,黑屏 |
| 把光标位置回传、在控制端重绘 | 换来一个 RTT 的延迟和 60Hz 的抖动,严格劣于浏览器原生光标 |

> ⚠️ **这条路同时带来一条不变量:远控配置只能经 `/api/rc/enable` 改。**
> 控制页手里的 `remoteControl` 是载入时的快照(`renderRemoteControl` 只回填复选框,
> 从不写回本地的 config 对象),而保存整个配置时会把这份陈旧快照一起发回来。
> 所以 `handleConfig` 里必须 `next.RemoteControl = old.RemoteControl` —— 不这么写,
> "开了远控之后再改一个视频参数"就会把 enabled 冲成 false,顺带清掉 Token 和
> 剪贴板开关,而远控监听还开着。这个 bug 在引入光标门控之前就存在(表现为配置和
> 实际不一致),光标门控只是把它变成了肉眼可见的故障:改个帧率,鼠标又开始拖了。

### 12.12 批准弹窗:右下角,当场点

有人申请控制时,主机不一定在控制页前面 —— 那个提示只在页面上,而申请
60 秒就作废(§12.6)。所以主机端加一个右下角弹窗,上面直接有「允许 / 拒绝」。

实现于 `internal/notify`(窗口)+ `popup.go`(状态机)。

#### 为什么是自己画的窗口

现成的三条路都走不通,这不是选择偏好:

| 路子 | 为什么不行 |
|---|---|
| `energye/systray` 的气泡通知 | 那个库**根本没有这个 API** —— 整个模块里 `NIF_INFO` 从未被设置过 |
| Windows 气泡通知(`NIF_INFO`) | 本身**不支持按钮**,而且 Win10 以后被系统转成 toast,点击回调不一定触发 |
| WinRT toast | 要 AUMID + 开始菜单快捷方式 + 注册 COM 激活器,为一个批准框不值当 |
| `MessageBoxW` | 模态、居中、**没有超时**,不能自动消失 |

所以自己 `RegisterClassExW` + 消息循环,和本程序处理 Win32 的一贯方式一致。

界面是**全自绘**的:系统控件的三维边框和主题去不掉,要扁平化就只能自己
画(圆角卡片 + 两个圆角按钮 + `DrawTextW`)。代价是 Tab 之类的键盘导航
没有了 —— 与"不要用键盘确认"的方向一致。

#### 抢焦点,但 Enter 不产生任何效果

弹窗会主动抢前台(主人此刻多半在别的地方,不抢就不会被注意到)。这带来
一个必须处理的风险:抢焦点的那一刻,用户正在别处敲键盘,而**那个回车很
可能是打给别的窗口的**。

所以回车被**显式吃掉**并且不产生任何选择。注意"不产生效果"不等于
"不管它":只要不截获,回车就会落到对话框管理器手里去激活默认按钮。
两道都要有 —— 截获 + 按钮不是系统控件、没有默认按钮这回事。

「允许」只能鼠标点;`Esc` 是拒绝(它不是"确认"键,方向是安全的)。

同一个理由见 `dialog_windows.go` 里 `ask()` 的 `MB_DEFBUTTON2`。

#### 倒计时

正文第二行是每秒刷新的"N 秒后自动拒绝",由窗口自己的 `SetTimer`(1 秒)
驱动,只重绘正文那一块 —— 整张卡重绘会闪。

秒数**不烤进正文文本**:正文是弹窗创建时算一次的,秒数一旦写进去就永远
定格在弹出那一刻。窗口只存一个作废时刻(`deadline`),每秒按剩余时间现算。
向上取整,否则弹窗一出来就显示 59,看着像已经过了一秒。

#### 不点会怎样:弹窗自己不发送任何东西

倒计时归零后弹窗只是自己消失,**不替用户发拒绝**。过期逻辑仍然只在
`remotectl` 一处(`expireLoop`),弹窗不做第二份决定。

> 文案上写的是"自动拒绝",而机制上是"主机没有应答" —— 这两个不矛盾:
> 申请在控制权状态机里最终确实是 `denied`,所以对用户说"自动拒绝"没有错;
> 只是拒绝的**原因**写的是"主机没有应答"而不是"主机拒绝了这次申请",
> 协议上分得开。
>
> 但要小心:别因为文案这么写,就顺手在 `popup.go` 的超时分支里补一个
> `Deny` 调用。那就重复了,而且观众收到的原因也会跟着变成"主机拒绝了
> 这次申请" —— 那是另一回事。

#### 状态机:盯跃迁,不是盯回调

`remotectl` 的 `OnChange` 在**每一次**主机可见的状态变化时都会触发:有人
连上、申请、批准、拒绝、收回、断开、开关、过期。照着回调弹窗,同一份申请
会被弹好几次。所以 `popup.go` 只认 `Pending` 的跃迁。

还有两个必须挡的:

- **陈旧回调。** `OnChange` 没有全局串行化(两条 readPump 协程 + 过期定时器
  都可能调它,各自先取一份 `Status` 再进来)。一条在申请出现**之前**取到的、
  内容是"没有申请"的状态如果晚到一步,会把刚弹出来的窗关掉 —— 而此后不会
  再有回调来提醒主人。所以动手之前要再问一次权威状态。
  > 这条依赖 `remotectl` 的一个不变量:**`notify()` 从不在持有 `s.mu` 时被调
  > 用**。也就是说 `Status()` 可以从 `OnChange` 里安全调用。哪天有人在
  > `s.mu` 里调 `notify`,这里会立刻自死锁(Go 的 mutex 不可重入)。
- **决定之后回调又来。** 批准/拒绝会自己再触发一轮 `OnChange`,不能因此
  再弹一次。

#### 实测踩到的两个坑

都是"放错 dll 不是降级,而是直接 panic"这一类 —— `LazyProc.Call` 找不到
过程时**会 panic**,不是返回错误:

```
panic: Failed to find GetCurrentThreadId procedure in user32.dll
panic: Failed to find DrawTextW procedure in gdi32.dll
```

`GetCurrentThreadId` 在 kernel32;`DrawTextW` 在 user32。这类错误静态看
代码看不出来,只能在真机上把窗口跑起来才会暴露 —— 所以这个功能是先用
一个临时探针把窗口单独跑通(建窗、定位、抢焦点、按键、点击、超时各验一遍)
之后才接进主程序的。

#### 已知局限

- **独占全屏的程序会盖住它**(无边框全屏游戏不影响)。这是 Win32 的规则,
  `HWND_TOPMOST` 也压不住。托盘提示文字(`remoteStatusText`)仍然是兜底信号。
- **锁屏 / UAC 安全桌面上看不到**,`SetForegroundWindow` 也会失败 —— 那种
  情况只让它以 TOPMOST 显示出来,不报错,申请自然过期。
- 混 DPI 的多显示器下按主屏比例渲染:`GetDpiForSystem` 在创建窗口**之前**
  就要用,而那时候还没有窗口可以问 `GetDpiForWindow`。

### A.3 完整推流命令

**默认档位:1280×800 @ 60fps @ 3 Mbps**(理由见 §6.3 / §7.6.5)。**完整命令见 §6.3**,此处只列各种采集源的输入段。

**三种采集源(直接替换完整命令里的输入部分):**

| 采集源 | 输入参数 |
|---|---|
| 屏幕(gdigrab,**默认**) | `-f gdigrab -framerate 60 -i desktop -vf "scale=1280:800"` |
| 屏幕(ddagrab,更快) | `-f lavfi -i "ddagrab=framerate=60" -vf "hwdownload,format=bgra,scale=1280:800"` |
| 窗口(**只能用 gdigrab**) | `-f gdigrab -framerate 60 -i title="窗口标题" -vf "scale=1280:800"` |
| OBS 虚拟摄像头 | `-f dshow -framerate 60 -i video="OBS Virtual Camera" -vf "scale=1280:800"` |

> ⚠️ **ddagrab 不支持单窗口采集**,窗口源只能走 gdigrab —— 而 gdigrab 在半分辨率下抓窗口时性能会明显下降,且**窗口被遮挡会抓到遮挡物**。

> 上表是**远控关闭**时的样子。远控开启时程序会给输入段多带一个禁用光标的选项:
> ddagrab 是滤镜内联的 `:draw_mouse=0`,gdigrab 是 `-i` 之前的 `-draw_mouse 0`
> (它是输入选项,不是滤镜,放进 `-vf` 会被拒绝)。理由见
> [§12.11](#1211-光标控制者看自己的)。

**软件编码兜底:** 把 `-c:v h264_nvenc -preset p4 -tune ll` 换成 `-c:v libx264 -preset ultrafast -tune zerolatency`。

**输出段(程序当前的写法):**

```
-f rtsp -rtsp_transport tcp rtsp://127.0.0.1:8554/live
```

带音频时,输入段里还要多一路 PCM(见 §5.5):

```
-f f32le -ar 48000 -ac 2 -i tcp://127.0.0.1:<系统分配的端口>
```

音频是程序用 WASAPI 回环采下来、经本地 TCP 送进 ffmpeg 的。采样格式、采样率、
声道数**照抄设备的混音格式**,不能写死成 48kHz 立体声 —— 共享模式下格式由
音频引擎决定,应用无权指定。对应地,音频编码固定为 `-c:a libopus`。

**改用 SRT 推流(更低延迟):** 把输出段换成

```
-f mpegts "srt://127.0.0.1:8890?streamid=publish:live"
```

⚠️ SRT 走 MPEG-TS 封装,带不了 Opus,所以换过去就没声音了。

**加鉴权(公网部署后):** 推流地址改为

```
-f rtsp "rtsp://publisher:<推流密码>@127.0.0.1:8554/live"
```

### A.4 观看地址

| 地址 | 说明 |
|---|---|
| `http://localhost:8889/live` | 本机观看(Stage 0 调试用) |
| `http://<局域网IP>:8889/live` | 局域网内设备观看 |
| `https://share.<域名>:8443/live` | **公网观看**(正式地址,带鉴权) |

⚠️ 局域网内观众**不要用公网域名访问** —— 流量会绕到公网再回来,消耗上行带宽,而且很多路由器不支持这种回环(hairpin NAT)导致直接连不上。

## 附录 B:MediaMTX 关键配置

### B.1 公网部署配置(正式配置)

```yaml
# ── WebRTC / WHEP 服务(对公网) ──
webrtc: yes
webrtcAddress: :8443              # 播放端口,改非标端口减少被扫
webrtcEncryption: yes             # 强制 TLS (§7.6)
webrtcServerKey: server.key
webrtcServerCert: server.crt
webrtcLocalUDPAddress: :8189      # 媒体流 UDP,必须映射到公网
webrtcAllowOrigin: '*'

# ── ICE 候选(公网成败关键,§7.6.4) ──
webrtcIPsFromInterfaces: no       # 关掉内网 IP 收集
webrtcAdditionalHosts: [share.example.com]   # 填 DDNS 域名

# ── 推流入口(仅本机,不映射到公网,§7.5) ──
rtmp: yes
rtmpAddress: 127.0.0.1:1935       # 绑定回环,而非 0.0.0.0
srt: yes
srtAddress: 127.0.0.1:8890

# ── 路径与鉴权(公网必须开启,§7.5) ──
paths:
  live:
    readUser: viewer
    readPass: <播放密码>
    publishUser: publisher
    publishPass: <推流密码>
```

### B.2 Stage 0 调试配置(先在局域网验证链路)

```yaml
webrtc: yes
webrtcAddress: :8889
webrtcLocalUDPAddress: :8189
webrtcAllowOrigin: '*'
webrtcIPsFromInterfaces: yes      # 局域网自动收集本机 IP

rtmp: yes
rtmpAddress: :1935
srt: yes
srtAddress: :8890

paths:
  live:
```

先用这套跑通 Stage 0 和 Stage 1,确认采集、编码、播放链路没问题,**再换成 B.1 打通公网**。这样出问题时能明确区分是"链路本身不行"还是"公网配置不对"。

若局域网访问异常(其他设备连不上),在 B.2 基础上增加:

```yaml
webrtcAdditionalHosts: [192.168.1.100]
```
